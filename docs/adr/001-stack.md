# ADR-001. Стек сервиса Poker Monte Carlo

Статус: принято. Первоначальное решение: 03.09.2026. Уточнение: 02.11.2026.

## Контекст

Нам нужен не только HTTP-метод расчёта шансов: нужны форма покерной раздачи, вход,
история задач конкретного пользователя и администратор для создания аккаунтов.
Расчёты до 200 000 симуляций занимают секунды, поэтому их запуск и хранение результата
должны быть отделены от обработки HTTP. Команда из четырёх человек делит работу на
ядро, веб, API/сервисы и инфраструктуру; менять интерфейс не должно означать переписывать симулятор.

## Варианты

| Вариант | Что удобно именно для покера | Цена |
|---------|-----------------------------|------|
| Django + Django Ninja | ORM хранит задачи, сессии изолируют историю, формы и шаблоны дают интерфейс, Ninja описывает API на pydantic | Нужно освоить соглашения Django, миграции и границы между формами, API и сервисами |
| FastAPI | Удобно описать вход раздачи и API, есть pydantic | Для нашего сайта отдельно потребуются ORM, миграции, вход, админка и сборка страниц |
| Flask | Небольшой HTTP-слой легко начать | Вход, валидация, схема API и работа с БД потребуют больше собственного кода и согласования между участниками |

## Решение

Оставляем Python 3.14 (минимум 3.12), Django 5.x и Django Ninja. Одна схема `PokerParams`
проверяет карты, повторы и лимиты до расчёта. Веб и API обращаются к `web/services.py`,
а ядро сохраняет контракт `run(params: dict) -> dict` без Django и базы данных.

Силу комбинаций оценивает `treys`: самостоятельно реализовывать все комбинации и сравнение
кикеров в рамках курса рискованнее. Симуляция остаётся на Python; NumPy и JIT не подключаем,
пока нет измеренной потребности и соответствующего решения.

Для простого локального запуска используем SQLite; в Docker — PostgreSQL, чтобы веб и воркер
работали с общей БД. Redis/RQ хранит очередь `calc`, а не кэш результатов. Статику под gunicorn отдаёт
WhiteNoise — сжатие из `STATIC_ROOT` без отдельного веб-сервера. Для локального режима
без Redis предусмотрен фоновый поток; это отдельное решение [ADR-002](002-background-thread.md).

## Последствия

- Вход, формы, хранение истории и админка используют готовые возможности Django.
- Ядро можно запускать и тестировать через CLI без веб-сервера; оно не зависит от ORM.
- При изменении данных нужны миграции; дублирование бизнес-правил в API и views запрещено.
- За вычисления на Python платим временем симуляции. Фоновый запуск освобождает HTTP-запрос,
  но не ускоряет математический расчёт.
- Для очереди нужны отдельные Redis и воркер; без запущенного воркера задача остаётся PENDING.
- Статику из `STATIC_ROOT` отдаёт WhiteNoise, поэтому gunicorn и Docker работают без
  отдельного веб-сервера; цена — `collectstatic` при сборке образа и сжатие на лету.
- Точность ограничена числом симуляций и моделью случайных рук; это учебная рекомендация,
  а не полноценная стратегия игры против конкретных соперников.
