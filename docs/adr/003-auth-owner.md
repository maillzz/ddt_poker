# ADR-003. Вход по сессии Django и владелец задачи

**Статус:** принято
**Дата:** 2026-10-01

## Контекст
Аудит безопасности (`docs/security_review.md`) показал: аноним мог создавать задачи, а любой —
читать чужие по номеру (`GET /api/tasks/{id}`, `/tasks/{id}/`). У `Task` не было владельца.
Пользователи — студенты и преподаватель, один сервер, сайт и API в одном Django-приложении.

## Рассмотренные варианты
1. **Сессия Django (`django.contrib.auth`) + `SessionAuth` в Ninja** — уже есть в Django: вход, пароли, админка,
   CSRF; сайт и API используют одну сессию, страница задачи опрашивает API без доп. настройки.
   Минус: внешнему клиенту (скрипту) нужно сначала войти и передавать CSRF-токен.
2. **Токены (API-ключ / JWT)** — удобно скриптам, не нужен CSRF; но нужна выдача, хранение и отзыв ключей,
   новая зависимость для JWT, а сайту всё равно нужна сессия.
3. **Без входа, «секретная» ссылка на задачу** — просто, но ссылку легко переслать или перебрать.

## Решение
Вариант 1. Все страницы — `@login_required` (вход `/accounts/login/`), все эндпоинты API — сессионная
аутентификация с проверкой CSRF на POST (сначала вход → 401, потом CSRF → 403). У `Task` поле `owner`
(FK на пользователя, `CASCADE`); все функции `web/services.py` принимают `owner` и фильтруют по нему.
Чужая задача отвечает 404 — как несуществующая, чтобы по кодам нельзя было узнать, какие номера заняты.

## Последствия
- Изоляция данных в одном месте — сервисном слое; view и API не могут «забыть» фильтр, не вызвав сервис.
- Нет регистрации: пользователей создаёт администратор (`createsuperuser`, админка).
- Задачи, созданные до миграции `0002`, без владельца — не видны никому, кроме админки.
- Если понадобится доступ скриптам без браузера — добавить токен-аутентификацию вторым методом (новый ADR).
