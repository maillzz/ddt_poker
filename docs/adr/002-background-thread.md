# ADR-002. Расчёт задачи в фоновом потоке вместо синхронного выполнения в HTTP-запросе

**Статус:** принято
**Дата:** 2026-09-30

## Контекст
`POST /api/tasks` и форма `/tasks/new/` вызывали `services.create_and_run`, который
выполнял `execute_task` прямо внутри HTTP-запроса. Время ответа росло линейно с числом
симуляций: 200 000 симуляций против 9 соперников — около 22–28 секунд, всё это время
браузер «висел», а один воркер сервера был занят. Страница задачи (`detail.html`) уже
умеет опрашивать `GET /api/tasks/{id}` раз в 1,5 секунды, но при синхронном расчёте
пользователь попадал на неё, когда задача уже была FINISHED. Полноценная очередь
RQ + Redis (`USE_QUEUE=1`, заезд 2) требует отдельного процесса-воркера и Redis.

## Рассмотренные варианты
1. **Оставить синхронно** — просто, но ответ ждёт весь расчёт; упирается в таймауты
   прокси/gunicorn (обычно 30–60 с) уже на больших задачах.
2. **Очередь RQ + Redis** — надёжно (задачи переживают перезапуск, воркеры
   масштабируются), но нужен Redis и отдельный процесс; остаётся за флагом `USE_QUEUE=1`.
3. **Фоновый поток `threading.Thread` в том же процессе** — встроенный модуль Python,
   без новых зависимостей и инфраструктуры; ответ уходит сразу.

## Решение
При `USE_QUEUE=0` (по умолчанию) `create_and_run` создаёт `Task` в статусе PENDING и
запускает `execute_task(task.id)` в `threading.Thread(daemon=True)`, после чего сразу
возвращает задачу: API отвечает `202 {id, status}`, форма — редиректом на страницу
задачи. Поток сам переводит задачу RUNNING → FINISHED/FAILED (статусы по-прежнему
меняются только в `execute_task`, AGENTS.md п.3). Поток стартует через
`transaction.on_commit`, чтобы его соединение с БД гарантированно видело строку задачи,
и закрывает своё соединение по окончании. Итоговый статус пользователь получает опросом
`GET /api/tasks/{id}` — это уже делает `detail.html`; API и views не менялись по смыслу.

## Последствия
- Ответ POST — миллисекунды независимо от размера задачи (замеры — в README).
- Потоки живут внутри веб-процесса: при его перезапуске (деплой, `runserver`-автоперезагрузка,
  падение) идущие расчёты теряются, задача навсегда остаётся RUNNING. Повторного запуска нет.
- Нет ограничения параллелизма: N одновременных POST — N потоков в одном процессе.
- Расчёт CPU-bound, а GIL общий: во время расчёта остальные запросы этого процесса
  отвечают медленнее (замер: GET статуса ~120 мс вместо ~5 мс), сам расчёт — на ~5% дольше.
- С несколькими процессами gunicorn задача считается в том процессе, который принял POST, —
  это работает, но нагрузка распределяется случайно.
- SQLite: запись из потока конкурирует с записью из запросов (ждёт блокировку до 5 с).
  Тесты используют файловую тестовую БД (`TEST.NAME` в settings) и `django_db(transaction=True)`.
- Для продакшена и больших нагрузок правильный путь — `USE_QUEUE=1` (RQ + Redis);
  поток — промежуточное решение без новой инфраструктуры.
